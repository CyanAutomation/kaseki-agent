# Investigation and fix plan: kaseki-449, kaseki-450, kaseki-451

Investigated 15 October 2026 through authenticated API requests, SSH host inspection, native-runtime smoke tests, and source inspection. Missing operational artifacts for 450 were recovered without replacing its API timeout outcome. No runs were retried and no deployment or kernel settings were changed. Credentials are intentionally omitted.

## Findings

| Run | API elapsed time | Confirmed failure | Confidence |
| --- | --- | --- | --- |
| kaseki-449 | 1,509 seconds | Pre-agent `npm run verify && npm run lint` timed out after 300 seconds; auth-worker workerd processes crashed first | High |
| kaseki-450 | 3,600 seconds | Deadline expired during corrective coding after a flaky browser-test failure; worker evidence was stranded in a nested staging directory | High |
| kaseki-451 | 1,069 seconds | Same pre-agent command timeout and workerd crash as 449 | High |

For 449 and 451, goal setting, scouting, and coding never started, and no code changes were produced. Exit 124 is the final timeout symptom. The root failure visible in both runs is native runtime startup during `auth-worker:verify`, after the earlier application tests had run.

The command expands to `npm run test:all && npm run auth-worker:verify && npm run plugin:maturity:check && npm run typecheck && npm run build && npm run go:test`, followed by lint only if verify succeeds. `auth-worker:verify` installs the nested auth-worker dependencies and starts Vitest's Cloudflare worker pool. The logs identify workerd version `1.20261006.1` and Linux ARM64 dependency caches.

Workerd emits `MmapAligned() failed`, reports that TCMalloc assumes a 48-bit virtual address space, and aborts while allocating internal allocator data. Vitest subsequently reports `write EPIPE`, failed Cloudflare pool startup, a runner startup timeout, and no tests executed in that pool. The pre-agent command eventually reaches Kaseki's 300-second limit.

The independent baseline validation also encounters the same allocator crash before the agent starts. Baseline exits were 1 after 247 seconds in 449 and 218 seconds in 451; pre-agent executions both lasted 301 seconds and exited 124. This establishes an existing environment/runtime failure, rather than an agent-introduced regression.

SSH confirmed that execution host `192.168.88.201` is a Raspberry Pi 4 Model B running Linux `6.18.33+rpt-rpi-v8`, with `CONFIG_ARM64_VA_BITS_39=y` and `CONFIG_ARM64_VA_BITS=39`; 48-bit and 52-bit addressing are disabled. Its virtual-memory limit is unlimited. A bounded actual-worker smoke of the cached binary reproduced the identical TCMalloc abort on the host. The same workerd version passed an actual-worker smoke on the development machine. The address-space incompatibility is confirmed; increasing the validation deadline or adding swap cannot fix it.

Upstream corroboration: [Cloudflare workerd issue 5020](https://github.com/cloudflare/workerd/issues/5020) contains the same allocator failure signature; [workers-sdk issue 11362](https://github.com/cloudflare/workers-sdk/issues/11362) reports an ARM64 TCMalloc startup crash and EPIPE. Neither proves this host's kernel configuration or establishes an available fixed release.

## Recovered explanation for 450

SSH revealed `/agents/kaseki-results/kaseki-450/.staging-result-kaseki-450-Kh05zj/`, which contained the worker logs, events, diff, validation results, and goal-check evidence absent from the API. The API finalizer had created the terminal result directory while the host wrapper still held a staging directory. Plain `mv staging final` then nested the directory instead of promoting its files.

Baseline and pre-agent build/test/lint both passed. Goal setting completed, scouting failed its artifact contract twice and used a conservative fallback, and coding changed two documentation files. The post-change build passed in 308 seconds. The next command failed in 118 seconds because `src/components/version-history-modal.test.ts` generated asynchronous activity after its failed-fetch test ended, raising `ReferenceError: window is not defined`. Goal check returned unmet and a corrective coding attempt began. The API's one-hour deadline then interrupted that attempt. This run used `npm run build;npm run test:all && npm run lint`, which excluded auth-worker verification; it did not encounter the workerd blocker from 449/451.

The causality report wrongly identified a timeout as pre-existing infrastructure failure: its broad `/timeout/i` marker matched successful test names in the log. It is not evidence that the browser-test failure was caused by infrastructure. The documentation-only diff and late DOM teardown are consistent with a test/component lifecycle race.

The missing registered operational artifacts were copied into the final directory without overwriting the authoritative timeout metadata or deleting the staging originals. These are now available to the API. Its original fallback summary and metadata remain historical API-finalization evidence.

## Additional diagnostic defects

1. The comparison artifact correctly sets `baseline_comparison_reliable: false` because working validation never ran. The status endpoint incorrectly returns `baselineComparisonReliable: true`: `src/utils/status-response-artifact-helper.ts`, in `extractBaselineComparisonSummary`, infers reliability only from the baseline exit code and discards the artifact's explicit reliability flag and warning. Zero classified failures here means unavailable comparison, not successful validation.
2. `metadata.json` reports `validation_infrastructure_diagnostics.infrastructure_failure: false` despite the native runtime crash. Current pipeline diagnostics do not adequately classify subprocess startup failures with a successful tee/filter pipeline.
3. The timeout message references `validation-command-diagnostics.log`, but that file is absent from the available artifact lists. Preserve the referenced detail through consolidation or point the message to an accessible artifact.
4. `src/job-scheduler.ts` cleans up the container in the timeout path before writing fallback artifacts. It does not use its existing Docker log-tail helper there. Bootstrap-log persistence is present in the ordinary failure path, but absent from this timeout path. This is a concrete opportunity to improve evidence retention; it does not prove why 450 originally produced no worker artifacts.
5. Status reports a 10,800-second phase-health timeout while 450's persisted effective orchestration deadline was 3,600 seconds. Display the deadline that actually governed the run.

## Ordered remediation

### 1. Confirm and remove the runtime blocker

- On the execution host and inside the actual worker image, capture architecture, kernel version, page size, kernel `CONFIG_ARM64_VA_BITS*` where available, `ulimit -v`, `/proc/self/limits`, and container memory/PID limits. Inspect the host kernel's OOM events. Do not dump the environment or credentials.
- Run a short, bounded workerd startup smoke with the exact locked binary, then the smallest auth-worker integration test. Capture stderr, signal, and exit code. A version-only command may not exercise allocator initialization sufficiently; use an actual minimal worker startup.
- Recommended immediate recovery: execute these validations on a host verified to start the locked workerd binary, such as an appropriate x86-64 runner, and confirm full auth-worker tests there before resuming coding runs. Linux ARM64 support alone does not guarantee compatibility with this host's kernel address-space configuration.
- If ARM64 execution must remain local, choose a kernel/platform verified to satisfy this binary's mapping requirements, or evaluate a compatible workerd build with an appropriately configured allocator. A kernel or platform change needs a separate rollout and rollback plan; a Docker image change alone cannot change the host kernel's virtual-address capabilities. Do not assume an arbitrary upgrade or downgrade fixes this.
- Keep auth integration validation mandatory. Increasing timeouts, swap, or skipping tests does not remedy a deterministic runtime startup crash.

Acceptance: minimal worker startup and the auth-worker integration suite execute tests successfully in the intended worker environment, with no allocator fatal errors, EPIPE, or core dumps.

### 2. Make validation failures specific and budgets measurable

- Add a bounded capability smoke before the expensive full validation when a repository requires workerd. Classify startup failure as a runtime/environment incompatibility with the relevant subcommand and stderr evidence.
- Separate the opaque combined verification command into supported, semicolon-separated validation stages: application tests, auth-worker verification, maturity checks, typecheck, build, Go tests, and lint. Preserve ordering and fail-fast behavior.
- `scripts/validation-timeout-policy.sh` currently gives `npm run verify && npm run lint` 300 seconds because its text contains no build command, although verify internally includes a build and many suites. Measure each healthy stage on the chosen host and set bounded budgets with sufficient headroom. Verify configuration is forwarded into workers before relying on a timeout override.
- Review repeated baseline and pre-agent work and nested `npm ci` costs only after correctness is restored. Any reuse must preserve commit, command, dependency, and environment identity, including runtime compatibility.

Acceptance: each stage has an identifiable result and duration; injected runtime crashes fail promptly with the underlying cause; healthy builds fit measured budgets without disabling checks.

### 3. Retain evidence on deadline expiry

- In the scheduler timeout path, persist controller stdout/stderr tails, last actual stage, effective deadline, and a bounded Docker log/inspection snapshot before forced removal. Make this best effort and bounded so cleanup still completes.
- Where supported, request graceful worker termination and allow a short finalization window before forced cleanup. Preserve existing nonempty artifacts and the original timeout cause.
- Record worker image digest/version and relevant host capabilities. Runs 449 and 451 currently have unknown runner version and null image identity.
- Repair status reliability handling by honoring the canonical comparison flag and warning. Classify native runtime startup failures separately from test assertions and timeout symptoms. Keep diagnostic references accessible after artifact consolidation.

Acceptance: a test run deliberately stalled before initialization still retains useful logs and the last known stage after timeout; cleanup succeeds; status reflects the actual effective deadline and an unreliable baseline comparison remains unreliable.

### 4. Regression verification and controlled recovery

- Add focused scheduler tests for deadline expiry before worker artifacts exist, bounded log capture before removal, preservation of existing artifacts, and log-capture failure that does not block cleanup.
- Add API coverage for baseline exit 1 combined with `baseline_comparison_reliable: false` and an unavailable or timed-out working result.
- Add validation classification coverage using the observed TCMalloc/EPIPE signature and ensure no-tests-executed runtime startup failures cannot be treated as reusable ordinary test outcomes.
- Run a validation-only check in the repaired execution environment, followed by one normal canary task. Require successful baseline/pre-agent validation and entry into agent phases before retrying further work.
- Retry 449 and 451 only after workerd compatibility is restored. Apply the Matmetrics release-history lifecycle fix before retrying 450, and allow a measured total run budget that covers baseline, pre-agent validation, agent work, final validation, and possible corrective work.
