# Kaseki Agent environment inventory

Audit baseline: `main` at `d28d9756` (2026-10-12). This is a static repository audit; secrets were not read or copied. Line numbers below refer to this baseline; later implementation edits can shift current line numbers. This inventory separates runtime deployment settings from request payloads, process/container plumbing, test harness variables, and names that occur only in historical documentation.

## How to read the inventory

The current runtime does not have one central schema. `.agents/skills/environment-configuration/environment-variables.json` is a partial catalog used to generate published environment documentation, not a complete runtime manifest. The API uses `loadConfig()` in `src/kaseki-api-config.ts`; the scheduler projects request fields into worker environment in `src/job-scheduler.ts`; shell entry points set defaults in `run-kaseki.sh` and `kaseki-agent.sh`; gateway, JEV, Sentry, summarization, secret, and Soyuz modules read additional values directly. Docker Compose exposes another subset. Consequently an environment name can be a supported deployment input, an internal worker transport field, or an unvalidated incidental toggle. “Startup” means process/config load; “per run” means scheduler-created worker environment; “dynamic” means read when a function executes.

The repository-wide lexical scan found 192 distinct dotted `process.env.NAME` references in non-doc paths selected for the scan and 507 distinct `KASEKI_*`, provider, GitHub App, Cloudflare, and Sentry names across the whole repository (including tests, archived docs, skill material, and fixtures). Neither number is a count of supported settings. The latter is a search-result universe, not a purported runtime inventory. Tests and stale docs introduce many names not used by current production code. Indirect lookups include `validatePositiveInt(envVar, ...)`, the Soyuz adapter's `env[name]`, scheduler-injected environment maps, and shell variable expansion; every name in `.env.example`, `.env.template`, `.env.advanced.template`, `docker-compose.yml`, `docs/ENV_VARS.md`, and `docs/API.md` was checked against these paths. Retired names are listed separately below. `rg` cannot prove the absence of external deployment scripts, so operator-owned integrations remain an explicit unknown.

## Lifecycle coverage confirmed

Admission supports request-level repository/task, validation and allowlist properties in API schemas; JEV task admission screens tasks. Preparation clones the requested repo/ref and provisions Docker workers. Execution receives projected worker env, provider secrets, timeout and phase controls. Verification applies validation/quality/goal-check rules. Publish behavior is `publishMode` plus GitHub App credentials and server-side checks. Assessment uses JEV/evaluation and optional cost catalog. Authentication and webhook egress protections are server configuration/policy. Configuration for each phase is present, but there is no single uniform config loader; several controls are low-level direct reads. No evidence was found for a general caller override of GitHub App credentials, server auth, API bind, or webhook origin policy.
