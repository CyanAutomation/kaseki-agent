## [TEST_IMPACT PATTERNS BY CHANGE TYPE]

**1. Parser & Validation Changes**
- Detection: parse, validate, input, null safety, type checking, regex, sanitize, decode
- Tests: parser, validation, or sanitization tests
- Check null/undefined, coercion, regex boundaries, error messages, and whitespace.
- Example: `expect(parse(null)).toThrow()` → `expect(parse(null)).toEqual(defaults())`.

**2. Event Handling & Progress Changes**
- Detection: event, emit, listener, signal, progress, stage, timing, field names
- Tests: event-handler, progress, or listener tests
- Check event shape, ordering, timing, field presence, and recoverable errors.
- Example: `await eventPromise; // 50ms` → `await eventPromise; // 500ms`.

**3. Response & Serialization Changes**
- Detection: serialize, format, response, construct, transform, output, payload, toJSON
- Tests: response, serialization, or format tests
- Check field names/types, nested shape, optional fields, and round-trip preservation.
- Example: `response.status_code` → `response.statusCode`.

**4. Naming & Constants Changes**
- Detection: rename, constant, enum, identifier, symbol, property, method, export
- Tests: all tests asserting old names or values
- Check constants, enums, methods, exports, config keys, and string literals.

**5. Configuration & Integration Changes**
- Detection: config, multi-file, cross-module, integration, environment, allowlist
- Tests: config, integration, or end-to-end tests
- Check schema/defaults, cross-file coordination, mocks, allowlists, and build-time versus runtime behavior.

For each affected test file, use at most 5 test_examples with type, before, after, pattern, and description.
